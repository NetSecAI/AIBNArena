# Containerlab testbeds
This directory contains physical Containerlab YAML, reference states, and testbed-only assets. Scenario intent and thresholds do not live here.
Each testbed is selected by its `benchmarks/configs/testbeds/<name>.toml`: `sme01-small`, `sme01-dns`, `sme01-fw`, `sme01-qos`, `sme01-qos-greenfield` (the `sme01-qos` lab with another reference state), `campus_small`, `campus_medium` and `campus_large`, each campus lab with its `-greenfield` variant, `clos01` and `sme01-vlan`. Beyond `sme01-small`, the directories materialize focused VLAN, firewall, DNS, and QoS capabilities; `campus_medium` is a reference campus lab on its original Arista cEOS switches (an MLAG pair of aggregates, every access switch dual-homed to it by LACP, the firewall's `bond0` over it), combining all of them behind one firewall (the original's two merged on 2026-10-28), `campus_small` the same campus on two access switches, and `campus_large` the same campus grown to three buildings and ten VLANs. The three campus labs share a remote site behind their firewall, rendered by `benchmarks/testbeds/campus_site.py`, which is what lets every campaign scenario run on each of them. Each lab has its own name and management subnet, so several can be deployed at once -- with one exception: VyOS loads conntrack helpers into the host's kernel, and a firewall that does not load them (sme01-dns's) fails to commit its NAT while a campus firewall, which does, holds them.
```bash
containerlab deploy -t benchmarks/testbeds/containerlab/sme01-small/topology.clab.yml
containerlab destroy -t benchmarks/testbeds/containerlab/sme01-small/topology.clab.yml --cleanup
```
The shared lifecycle destroys and redeploys the testbed at the start of every episode, then applies the reference state. At the end, the experiment's `cleanup` either destroys the lab or restores the reference state and leaves it up. Generated `clab-*` directories are ignored.

The campus labs' switches are Arista cEOS (`ceos:4.36.1F`, the `arista_ceos` platform of `benchmarks/platforms/containerlab`). Three things about them are easy to trip on. Each lab's `ceos/startup.cfg` must stay: without a startup configuration cEOS boots into Zero Touch Provisioning, every port routed, and the reference state's sessions lose lines. containerlab mounts that file from the lab directory, so a lab copied to a path the Docker daemon does not see (a sandboxed `/tmp`, say) boots into ZTP the same way, silently. And a cEOS container takes about 90 s to boot and 1–1.5 GB of memory: `campus_large` holds eleven of them.
